# 1. 運用設計の目的

## 1.1 目的

本書は、AWS Financial AI Platformの安定稼働、安全な管理、障害発生時の復旧、コスト管理に必要な運用方法を定義する。

金融系システムを想定したインフラ運用の基礎を習得するため、以下を対象とする。

- EC2の起動・停止
- Apacheの稼働確認
- HTTP疎通確認
- Systems Managerによるサーバー管理
- 障害発生時の原因切り分け
- セキュリティグループの復旧
- AWS利用料金の確認
- 運用記録と変更履歴の管理

本環境は学習用であり、実際の金融取引、顧客情報、機密データの処理には使用しない。

## 1.2 実装ステータスの定義

本書では、各項目を次のように区別する。

| ステータス | 意味 |
|---|---|
| 構築済み | AWS上にリソースを作成済み |
| 検証済み | 実際に動作を確認済み |
| 設計済み | 手順・方針を定義済みだが、実行状況は未確認 |
| 未実装 | 今後構築・導入する予定 |

手順を文書化しただけでは、実施済みとは扱わない。

# 3. 運用体制

## 3.1 運用担当

現段階では、構築者本人が以下の役割を兼任する。

| 役割 | 担当業務 |
|---|---|
| インフラ管理 | AWSリソースの管理 |
| サーバー管理 | EC2・Apacheの管理 |
| 障害対応 | 調査・復旧・記録 |
| セキュリティ管理 | IAM・セキュリティグループ確認 |
| コスト管理 | 利用料金・不要リソース確認 |

本番環境では、責任者、承認者、障害連絡先、当番体制などを別途定義する必要がある。

## 3.2 運用時間

学習環境のため、24時間365日の稼働は要求しない。

- 学習・検証時のみEC2を稼働させる。
- 学習終了後は停止または終了を検討する。
- 不要なリソースは削除する。
- 停止中も発生する可能性がある料金を確認する。

# 4. 日常運用設計

## 4.1 EC2起動手順

**ステータス：設計済み**

1. AWSコンソールにログインする。
2. リージョンを東京に設定する。
3. EC2 → インスタンスを開く。
4. `financial-web-server` を選択する。
5. 「インスタンスの状態」→「インスタンスを開始」を選択する。
6. 状態が `Running` になるまで待つ。
7. ステータスチェックが `2/2` に合格することを確認する。

### 起動後の確認

- パブリックIPv4アドレス
- IAMロールの関連付け
- Session Managerの接続可否
- Apacheの稼働状態
- HTTP疎通

パブリックIPv4アドレスは、停止・起動によって変わる場合がある。

以前のIPアドレスを使い続けないこと。

## 4.2 EC2停止手順

**ステータス：設計済み**

1. 必要なスクリーンショットと作業記録を保存する。
2. 必要に応じてApacheの稼働状況を確認する。
3. EC2コンソールで対象インスタンスを選択する。
4. 「インスタンスの状態」→「インスタンスを停止」を選択する。
5. 状態が `Stopped` になったことを確認する。

### 注意事項

EC2を停止しても、EBSなどの料金が発生する場合がある。

EC2を終了すると、ルートボリュームなどが削除される場合があるため、必要なデータを保存してから操作する。

停止と終了を混同しない。

## 4.3 Apache稼働確認

**ステータス：確認手順設計済み**

Session ManagerでEC2に接続し、以下を実行する。

```bash
sudo systemctl is-active httpd
```

正常時の結果：

```text
active
```

詳細確認：

```bash
sudo systemctl status httpd
```

終了する場合は `q` キーを押す。

## 4.4 HTTP疎通確認

**ステータス：外部ブラウザ表示検証済み**

EC2内部から確認する。

```bash
curl -I http://localhost
```

正常時の期待結果：

```text
HTTP/1.1 200 OK
```

外部から確認する場合は、ブラウザで以下へアクセスする。

```text
http://<EC2のパブリックIPv4アドレス>
```

以下が表示されることを確認する。

```text
Hello World!

My AWS Financial AI Platform
```

実際にブラウザからの表示成功を確認済み。

HTTPは暗号化されないため、認証情報や機密データは送信しない。

# 5. サーバー管理設計

## 5.1 管理接続方式

**ステータス：検証済み**

EC2への管理接続には、AWS Systems Manager Session Managerを使用する。

以下の方式は採用しない。

- SSHポート22のインターネット公開
- SSHキーペアを使用した直接接続

## 5.2 IAM設定

IAMロール：

```text
financial-ec2-ssm-role
```

アタッチ済みポリシー：

```text
AmazonSSMManagedInstanceCore
```

IAMロールはEC2へ関連付け済み。

Session ManagerでEC2がOnlineと表示されることを確認済み。

## 5.3 接続手順

1. AWSコンソールでSystems Managerを開く。
2. Session Managerを選択する。
3. 「セッションの開始」をクリックする。
4. `financial-web-server` を選択する。
5. セッションを開始する。

接続後の確認例：

```bash
whoami
```

```bash
cat /etc/os-release
```

作業終了後はセッションを終了する。

## 5.4 接続できない場合の確認順序

1. EC2がRunningか。
2. ステータスチェックが正常か。
3. AWSリージョンが一致しているか。
4. IAMロールが関連付けられているか。
5. `AmazonSSMManagedInstanceCore` が付与されているか。
6. EC2からSystems Managerへの通信経路があるか。
7. セキュリティグループのアウトバウンドが許可されているか。
8. ルートテーブルとネットワークACLに問題がないか。
9. SSM Agentが正常に動作しているか。

SSM接続障害の解消を目的として、安易にSSHポート22を全世界へ開放しない。

# 6. 障害管理設計

## 6.1 障害レベル

以下は本学習環境における仮の分類である。

| レベル | 内容 | 対応方針 |
|---|---|---|
| 高 | EC2に接続できずWebも利用できない | 原因調査・復旧を優先 |
| 中 | Webに接続できないがSSMは利用可能 | Apache・通信経路を調査 |
| 低 | Webは正常だが一部の確認項目に異常 | 原因を記録して対応 |

本番環境での重要度、対応時間、連絡体制は別途定義する。

## 6.2 HTTP接続障害の切り分け

ブラウザからアクセスできない場合は、次の順序で調査する。

### ① EC2の状態確認

AWSコンソールで以下を確認する。

- Running
- ステータスチェック正常

### ② Apacheの状態確認

```bash
sudo systemctl is-active httpd
```

`active` でなければ、Apacheの状態を詳しく調査する。

```bash
sudo systemctl status httpd
```

### ③ EC2内部からHTTP確認

```bash
curl -I http://localhost
```

`200 OK` が返る場合、少なくともEC2内部からApacheへのHTTP通信は正常と判断できる。

### ④ セキュリティグループ確認

以下のインバウンドルールを確認する。

| タイプ | ポート | 送信元 |
|---|---|---|
| HTTP | TCP 80 | 0.0.0.0/0 |

### ⑤ ネットワーク確認

- パブリックIPv4アドレス
- インターネットゲートウェイ
- ルートテーブル
- ネットワークACL

以上を確認し、障害箇所を切り分ける。

# 7. 障害復旧設計

## 7.1 HTTP 80ルール削除による障害

**ステータス：障害対応テスト実施・GitHub記録済み**

### 障害概要

セキュリティグループのHTTP 80インバウンドルールを一時的に削除し、外部からWebページにアクセスできない状態を再現した。

### 調査方針

- EC2の稼働状態を確認する。
- Apacheの稼働状態を確認する。
- EC2内部からHTTP通信を確認する。
- セキュリティグループを確認する。

### 復旧手順

1. EC2コンソールを開く。
2. `financial-web-sg` を選択する。
3. インバウンドルールを編集する。
4. HTTP TCP 80のルールを再追加する。
5. ルールを保存する。
6. ブラウザでWebページを再表示する。

### 復旧判定

- HTTP 80ルールが復元されている。
- ブラウザからアクセスできる。
- Hello World!が表示される。

実際の障害発生時刻、復旧時刻、実測結果は、GitHubの障害対応記録を正本として管理する。

## 7.2 Apache停止時の復旧

**ステータス：手順設計済み・障害テスト未実施**

状態確認：

```bash
sudo systemctl status httpd
```

停止している場合の起動：

```bash
sudo systemctl start httpd
```

復旧確認：

```bash
sudo systemctl is-active httpd
```

```bash
curl -I http://localhost
```

期待結果：

```text
active
HTTP/1.1 200 OK
```

原因を調査せずに繰り返し再起動する運用は避ける。

# 10. セキュリティ運用

## 10.1 基本方針

- IAM権限は必要最小限とする。
- SSHポート22は公開しない。
- 管理接続にはSession Managerを使用する。
- 認証情報をGitHubに保存しない。
- 不要なインバウンドルールを作成しない。
- 変更前後に通信確認を行う。

## 10.2 現在の通信設定

| 通信 | 設定 |
|---|---|
| HTTP TCP 80 | 0.0.0.0/0から許可 |
| SSH TCP 22 | 許可ルールなし |
| アウトバウンド | 0.0.0.0/0への通信を許可 |

現在のHTTP公開は学習目的に限定する。

実際の金融系本番環境で、この設定をそのまま使用しない。

# 12. コスト管理

## 12.1 基本方針

**ステータス：運用方針設計済み**

学習環境のため、必要な時間だけAWSリソースを利用する。

- 不要なEC2を停止・終了する。
- 未使用EBSを確認する。
- 不要なElastic IPなどのリソースを確認する。
- NAT Gatewayは現時点で作成しない。
- AWS Billingで料金を確認する。

## 12.2 料金アラート

**ステータス：設定作業実施・通知動作は要確認**

確認対象：

- AWS Free Tier使用量アラート
- CloudWatch Billing Alarm
- SNS通知先メールアドレス
- AWS Budgets（必要に応じて導入）

料金アラートは通知を行う仕組みであり、リソースを自動停止するものではない。

## 12.3 学習終了時の確認

1. EC2の稼働状態を確認する。
2. 必要な成果物をGitHubに保存する。
3. EC2の停止または終了を判断する。
4. EBSなどの残存リソースを確認する。
5. AWS Billingで料金を確認する。

# 13. 変更管理

## 13.1 変更前の確認

AWS設定を変更する前に、以下を確認する。

- 変更対象
- 変更目的
- 影響範囲
- 現在の設定
- 復旧方法
- 必要な証跡

## 13.2 変更後の確認

変更後は以下を確認する。

- 設定が意図どおり反映されたか。
- HTTP通信に問題がないか。
- Session Manager接続に問題がないか。
- 不要なルールやリソースが残っていないか。

## 13.3 GitHub管理

設計書、障害対応記録、構成図をGitHubで管理する。

コミットメッセージ例：

```bash
git commit -m "docs: add operations design"
```

機密情報、AWS認証情報、秘密鍵、パスワードなどはコミットしない。
