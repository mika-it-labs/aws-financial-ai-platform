# 1. 運用設計の目的

## 1.1 目的

本書は、AWS Financial AI Platformの安定稼働、安全な管理、障害発生時の復旧、ネットワーク疎通確認、コスト管理に必要な運用方法を定義する。

金融系システムを想定したインフラ運用の基礎を習得するため、以下を対象とする。

- EC2の起動・停止
- Apacheの稼働確認
- HTTP疎通確認
- Systems Managerによるサーバー管理
- VPC PeeringによるVPC間通信確認
- 障害発生時の原因切り分け
- Security Groupの確認・復旧
- Route Tableの確認
- Terraformコードの管理
- AWS利用料金の確認
- 運用記録と変更履歴の管理

本環境は学習用であり、実際の金融取引、顧客情報、機密データの処理には使用しない。

## 1.2 実装ステータスの定義

| ステータス | 意味 |
|---|---|
| 構築済み | AWS上にリソースを作成済み |
| 検証済み | 実際に動作を確認済み |
| 設計済み | 手順・方針を定義済みだが、実行状況は未確認 |
| 未実装 | 今後構築・導入する予定 |

手順を文書化しただけでは実施済みとは扱わない。

# 3. 運用体制

## 3.1 運用担当

現段階では構築者本人が以下の役割を兼任する。

| 役割 | 担当業務 |
|---|---|
| インフラ管理 | AWSリソース管理 |
| ネットワーク管理 | VPC・Route Table・VPC Peering管理 |
| サーバー管理 | EC2・Apache管理 |
| 障害対応 | 調査・復旧・記録 |
| セキュリティ管理 | IAM・Security Group確認 |
| IaC管理 | Terraformコード管理 |
| コスト管理 | 利用料金・不要リソース確認 |

本番環境では責任者、承認者、障害連絡先、当番体制などを別途定義する。

## 3.2 運用時間

学習環境のため24時間365日の稼働は要求しない。

- 学習・検証時のみEC2を稼働させる。
- 学習終了後は停止または終了を検討する。
- 不要な検証用リソースは削除する。
- 停止中も料金が発生する可能性のあるリソースを確認する。

# 4. 日常運用設計

## 4.1 EC2起動確認

EC2起動後、以下を確認する。

```text
EC2
 ↓
Running
 ↓
Status Check
 ↓
IAM Role
 ↓
Session Manager
 ↓
Apache
 ↓
HTTP
```

確認対象：

- EC2がRunningであること
- ステータスチェックが正常であること
- IAMロールが関連付けられていること
- Session Managerから接続できること
- Apacheがactiveであること
- HTTP通信が正常であること

## 4.2 EC2停止

検証終了後、不要なEC2は停止する。

停止前に以下を確認する。

- 必要なスクリーンショットを保存したか
- GitHubへ必要な記録を保存したか
- EC2上に必要なデータが残っていないか

EC2停止後もEBS等の料金が発生する可能性があるため確認する。

## 4.3 Apache稼働確認

Session Managerから以下を実行する。

```bash
sudo systemctl is-active httpd
```

正常時：

```text
active
```

詳細確認：

```bash
sudo systemctl status httpd
```

## 4.4 HTTP疎通確認

EC2内部：

```bash
curl -I http://localhost
```

期待結果：

```text
HTTP/1.1 200 OK
```

VPC Peering経由：

```bash
curl http://10.0.1.124
```

正常時：

```html
<h1>Hello World!</h1><p>My AWS Financial AI Platform</p>
```

# 5. Systems Manager運用

## 5.1 管理方式

EC2への管理にはAWS Systems Manager Session Managerを使用する。

以下は原則使用しない。

- SSH TCP 22のインターネット公開
- SSHキーペアによる直接接続

IAMロール：

```text
financial-ec2-ssm-role
```

ポリシー：

```text
AmazonSSMManagedInstanceCore
```

## 5.2 SSM接続障害時

Session Managerから接続できない場合は以下を確認する。

```text
EC2 Running
    ↓
IAM Role
    ↓
AmazonSSMManagedInstanceCore
    ↓
Trust Relationship
    ↓
SSM Agent
    ↓
Security Group Outbound
    ↓
Route Table
    ↓
Internet / SSM Endpoint
```

SSM接続障害を解消する目的でSSH TCP 22を `0.0.0.0/0` へ開放しない。

# 6. VPC Peering運用

## 6.1 運用対象

```text
financial-ai-vpc
10.0.0.0/16
       │
       │ VPC Peering
       │
peering-lab-vpc
10.10.0.0/16
```

## 6.2 Route Table確認

financial-ai-vpc：

```text
10.10.0.0/16 → VPC Peering
```

peering-lab-vpc：

```text
10.0.0.0/16 → VPC Peering
```

Peering障害発生時は、Peering Connectionだけでなく双方のRoute Tableを確認する。

## 6.3 ICMP疎通確認

VPC間でpingを実行する。

```bash
ping -c 4 <接続先Private-IP>
```

検証結果：

```text
4 packets transmitted
4 received
0% packet loss
```

双方向通信を確認済み。

## 6.4 HTTP疎通確認

peering-lab-ec2から実行する。

```bash
curl http://10.0.1.124
```

検証結果：

```html
<h1>Hello World!</h1><p>My AWS Financial AI Platform</p>
```

VPC Peering経由のHTTP通信を確認済み。

# 7. 障害管理

## 7.1 障害切り分け

通信障害時は以下の順序を基本とする。

```text
VPC / Subnet
     ↓
VPC Peering
     ↓
Route Table
     ↓
Security Group
     ↓
OS
     ↓
Service
     ↓
Application
```

## 7.2 ICMP成功・HTTP失敗

pingが成功してもHTTPが失敗する場合、ネットワーク全体が停止しているとは判断しない。

確認する。

```text
ping OK
   ↓
Routeは概ね到達可能
   ↓
TCP 80 Security Group確認
   ↓
Apache状態確認
   ↓
curl localhost
   ↓
curl Private IP
```

今回の検証では、最終的に以下のレスポンスを取得した。

```html
<h1>Hello World!</h1><p>My AWS Financial AI Platform</p>
```

## 7.3 CIDR重複

既存VPCとの接続検討時に、双方で `10.0.0.0/16` が使用されていることを確認した。

CIDRが重複しているため直接Peeringせず、新たに以下を作成した。

```text
peering-lab-vpc
10.10.0.0/16
```

今後VPCを新規設計する場合は、VPC間接続を考慮してCIDR重複を避ける。

# 10. Terraform運用

## 10.1 現在の状態

AWS構成の一部をTerraformでコード化済み。

主な対象：

```text
VPC
Subnet
Internet Gateway
Route Table
Route Table Association
Security Group
IAM Role
IAM Instance Profile
EC2
```

以下を実行済み。

```bash
terraform validate
```

構文検証は成功している。

## 10.2 運用上の注意

既存AWSリソースがTerraform Stateへ取り込まれていないため、現段階では安易に以下を実行しない。

```bash
terraform apply
terraform destroy
```

既存環境をTerraform管理へ移行する場合は、実環境とコードの差分を確認した上で `terraform import` 等を検討する。

# 11. セキュリティ運用

基本方針：

- IAM権限は必要最小限とする。
- SSH TCP 22はインターネットへ公開しない。
- EC2管理にはSession Managerを使用する。
- AWS認証情報をGitHubへ保存しない。
- APIキーや秘密鍵をGitHubへ保存しない。
- Security Groupでは必要な通信のみ許可する。
- VPC間通信ではPrivate IPを利用する。
- 変更前後に通信確認を実施する。

# 13. コスト管理

本環境は学習用であるため、必要な時間だけAWSリソースを利用する。

- 不要なEC2を停止・終了する。
- 不要なEBSを確認する。
- Public IPv4等の料金発生対象を確認する。
- NAT Gatewayは現段階では作成しない。
- AWS Billingで利用状況を確認する。
- 検証終了後は不要なpeering-labリソースを削除する。
- 新しいサービス導入前に料金を確認する。

料金アラートは通知機能であり、リソースを自動停止するものではない。

# 14. 変更管理

AWS設定変更前に以下を確認する。

```text
変更対象
   ↓
変更目的
   ↓
影響範囲
   ↓
現在設定
   ↓
変更
   ↓
動作確認
   ↓
GitHub記録
```

変更後は以下を確認する。

- 設定が意図どおり反映されたか
- HTTP通信が正常か
- VPC Peering通信が正常か
- Session Managerが利用できるか
- 不要なSecurity Groupルールがないか
- 不要なAWSリソースが残っていないか
