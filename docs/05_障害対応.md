# 1. HTTP通信障害

## 1.1 障害概要

EC2上のApacheで公開しているWebページに、外部ブラウザからアクセスできない状態を意図的に再現した。

## 1.2 障害発生方法

Security Group `financial-web-sg` のインバウンドHTTP（TCP 80）ルールを一時的に削除した。

## 1.3 確認結果

| 確認対象 | 結果 |
|---|---|
| EC2 | Running |
| Apache | active |
| EC2内部 curl | HTTP 200 OK |
| 外部ブラウザ | アクセス失敗 |
| Security Group | HTTP 80許可なし |

## 1.4 原因

Apacheは正常に稼働していたが、Security GroupにHTTP TCP 80のインバウンド許可ルールが存在しなかった。

そのため、EC2内部では正常にHTTP通信できる一方、外部からのHTTP通信がSecurity Groupで遮断されていた。

```text
Internet
   │
   │ HTTP :80
   ▼
Security Group  ← 通信遮断
   ✕
   │
   ▼
EC2
   │
   ▼
Apache（active）
```

## 1.5 復旧対応

Security Groupへ以下のルールを再追加した。

```text
Type     : HTTP
Protocol : TCP
Port     : 80
Source   : 0.0.0.0/0
```

## 1.6 復旧確認

ブラウザから再度アクセスし、以下のWebページが表示されることを確認した。

```text
Hello World!

My AWS Financial AI Platform
```

**復旧結果：成功**

## 1.7 再発防止策

- Security Group変更前に現在の設定を確認する。
- 変更内容を記録する。
- 変更前後にHTTP通信確認を実施する。
- 障害発生時の復旧手順を記録する。
- 本番相当環境では `0.0.0.0/0` へのHTTP公開を避け、ALB等を利用した構成を検討する。

# 2. VPC Peering通信障害・切り分け

## 2.1 概要

異なるVPC間でPrivate IP通信を行うため、VPC Peeringを構築した。

接続対象：

```text
financial-ai-vpc
10.0.0.0/16
       │
       │ VPC Peering
       │
peering-lab-vpc
10.10.0.0/16
```

## 2.2 CIDR重複問題

当初、既存VPCとのVPC Peeringを検討したが、双方で以下のCIDRが使用されていた。

```text
10.0.0.0/16
```

CIDRが重複しているVPC同士はVPC Peeringできないため、接続先として新たに以下のVPCを構築した。

```text
peering-lab-vpc
10.10.0.0/16
```

### 対応結果

重複しないCIDRを使用することでVPC Peeringを構築できた。

### 学習事項

複数VPCを接続する可能性がある場合、VPC作成時点からCIDR重複を避けて設計する必要がある。

# 3. VPC Peering ICMP疎通確認

## 3.1 確認内容

VPC Peering構築後、Private IPを使用してEC2間の双方向通信を確認した。

```text
financial-web-server
        │
        │ Private IP
        ▼
    VPC Peering
        │
        ▼
peering-lab-ec2
```

## 3.2 確認項目

VPC Peering通信では以下を確認した。

```text
VPC Peering
     ↓
Route Table
     ↓
Security Group
     ↓
EC2
```

双方のRoute Tableへ相手VPCのCIDRを設定した。

```text
financial-ai-vpc
10.10.0.0/16 → VPC Peering

peering-lab-vpc
10.0.0.0/16 → VPC Peering
```

Security Groupでは、検証用として相手VPCからのICMP通信を許可した。

## 3.3 検証結果

双方向でpingを実施した。

結果：

```text
4 packets transmitted
4 received
0% packet loss
```

**結果：VPC Peering経由の双方向ICMP通信成功**

# 4. VPC Peering HTTP通信確認

## 4.1 現象

ICMPによるVPC間疎通確認後、`peering-lab-ec2` から `financial-web-server` へのHTTP通信を確認した。

ICMP通信が成功していても、HTTP通信は別途TCP 80およびApacheの状態を確認する必要がある。

## 4.2 切り分け

```text
ICMP
 ↓
成功
 ↓
Route Table確認
 ↓
Security Group TCP 80確認
 ↓
Apache確認
 ↓
HTTP curl
```

## 4.3 HTTP確認

`peering-lab-ec2` から以下を実行した。

```bash
curl http://10.0.1.124
```

最終結果：

```html
<h1>Hello World!</h1><p>My AWS Financial AI Platform</p>
```

**結果：VPC Peering経由のHTTP TCP 80通信成功**

## 4.4 学習事項

pingが成功していても、HTTPなどのアプリケーション通信が正常とは限らない。

HTTP通信障害では以下を個別に確認する必要がある。

- Route Table
- Security Group
- TCPポート
- OS
- Apache
- アプリケーション

# 5. Session Manager接続障害

## 5.1 障害概要

`peering-lab-ec2` 構築時、EC2自体はRunningであったが、Systems Manager Session Managerから接続できない状態が発生した。

## 5.2 確認内容

以下を順番に確認した。

```text
EC2 Running
    ↓
IAM Role
    ↓
AmazonSSMManagedInstanceCore
    ↓
Trust Relationship
    ↓
SSM Agent
    ↓
Network Route
```

## 5.3 IAM設定

使用IAMロール：

```text
financial-ec2-ssm-role
```

アタッチポリシー：

```text
AmazonSSMManagedInstanceCore
```

Trust Relationship：

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

IAMロール、ポリシー、Trust Relationshipおよびネットワーク経路を確認した。

## 5.4 復旧

IAMロールの関連付け状態等を再確認し、EC2の再起動後にSession Managerの接続状態を再確認した。

最終的にSession ManagerからEC2へ接続できることを確認した。

**復旧結果：成功**

## 5.5 再発防止・確認項目

新規EC2作成時は以下を確認する。

```text
EC2
 ↓
IAM Instance Profile
 ↓
financial-ec2-ssm-role
 ↓
AmazonSSMManagedInstanceCore
 ↓
SSM Agent
 ↓
Outbound Network
 ↓
Session Manager Online
```

SSM接続障害を理由にSSH TCP 22を `0.0.0.0/0` へ開放しない。

# 6. 障害切り分け標準フロー

今後の通信障害では、以下の順序を基本として原因を切り分ける。

```text
① EC2 Running?
        │
        ▼
② VPC / Subnet
        │
        ▼
③ VPC Peering
        │
        ▼
④ Route Table
        │
        ▼
⑤ Security Group
        │
        ▼
⑥ OS
        │
        ▼
⑦ Service
        │
        ▼
⑧ Application
```

HTTP障害の場合：

```text
curl localhost
      │
      ├── 成功
      │     ↓
      │  Apacheは正常
      │     ↓
      │  Network / SGを調査
      │
      └── 失敗
            ↓
         Apache / OSを調査
```

この切り分けによって、ネットワーク障害とアプリケーション障害を区別する。
