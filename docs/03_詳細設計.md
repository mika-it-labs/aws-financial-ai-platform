# 1. システム概要

## 1.1 目的

金融系システムを想定し、AWS上でWebサーバー基盤を設計・構築する。

本プロジェクトでは、以下の技術を習得する。

- AWSネットワークの設計・構築
- EC2によるWebサーバー構築
- IAMロールによる権限管理
- Systems Manager Session Managerによるサーバー管理
- セキュリティグループによる通信制御
- HTTP疎通確認
- 障害発生時の原因調査と復旧

本環境は学習用であり、実際の金融取引や顧客情報の処理には使用しない。

## 1.2 システム構成図

```text
              ユーザーPC
                  |
               HTTP:80
                  |
              Internet
                  |
          Internet Gateway
            financial-igw
                  |
       VPC: financial-ai-vpc
           10.0.0.0/16
                  |
      +-----------+-----------+
      |                       |
 Public Subnet           Private Subnet
 10.0.1.0/24             10.0.11.0/24
      |                       |
      |                 現時点では未使用
      |
 EC2: financial-web-server
      |
 Amazon Linux 2023
      |
 Apache HTTP Server
      |
 /var/www/html/index.html
      |

```

管理アクセスは以下の経路を使用する。

```text
管理者
  |
AWS Management Console
  |
Systems Manager
  |
Session Manager
  |
SSM Agent
  |

```

SSHポート22はインターネットへ公開しない。

- ネットワークの基本構造を理解しやすい構成とする。

# 4. セキュリティ詳細設計

## 4.1 セキュリティグループ

名前：

`financial-web-sg`

### インバウンドルール

| タイプ | プロトコル | ポート | 送信元 | 用途 |
|---|---|---|---|---|
| HTTP | TCP | 80 | 0.0.0.0/0 | 学習用Webページ公開 |

SSH（TCP 22）は設定しない。

### アウトバウンドルール

| タイプ | プロトコル | 送信先 |
|---|---|---|
| すべてのトラフィック | すべて | 0.0.0.0/0 |

現段階では学習とSSM通信のためにデフォルトの送信ルールを使用する。

将来的には、通信要件を整理した上で必要な送信先・ポートへの制限を検討する。

## 4.2 IAMロール

| 項目 | 設定値 |
|---|---|
| ロール名 | financial-ec2-ssm-role |
| 信頼されたエンティティ | EC2 |
| 許可ポリシー | AmazonSSMManagedInstanceCore |
| 用途 | EC2からSystems Managerを利用するための権限 |

EC2インスタンスにIAMロールを関連付け済み。

IAMロールとインスタンスプロファイルを通じて、SSM Agentに必要な権限を提供する。

## 4.3 Session Manager

管理者はAWSコンソールのSession ManagerからEC2に接続する。

設計方針：

- SSHポート22を開放しない。
- SSHキーペアを使用しない。
- EC2にIAMロールを関連付ける。
- SSM AgentからSystems Managerへの通信を確保する。

確認済み項目：

- EC2：Running
- EC2ステータスチェック：2/2合格
- パブリックIPv4：あり
- IAMロール：関連付け済み
- AmazonSSMManagedInstanceCore：付与済み
- アウトバウンド通信：許可済み
- インターネットゲートウェイへのルート：有効
- Session Manager：対象EC2がOnlineとして表示

## 4.4 セキュリティ上の制約

本構成は学習用であり、金融系本番環境の要件を満たすものではない。

現在の制約：

- HTTP通信は暗号化されていない。
- EC2がパブリックサブネットに存在する。
- HTTP 80を全IPv4アドレスに公開している。
- 単一AZ・単一EC2構成であり、冗長化していない。
- 監視・監査ログ・バックアップなどの本番要件は未整備。

本番相当の構成へ拡張する場合は、HTTPS、ALB、プライベートEC2、VPCエンドポイント、最小権限、監視、ログ保管、バックアップ、複数AZなどを検討する。

# 6. 障害対応テスト設計

## 6.1 テスト目的

Webサーバーにアクセスできない障害を意図的に発生させ、原因の切り分けと復旧を練習する。

対象は学習用EC2のみとする。

## 6.2 障害発生方法

セキュリティグループ `financial-web-sg` から、HTTP TCP 80のインバウンドルールを一時的に削除する。

IAMロール、アウトバウンドルール、SSH設定は変更しない。

## 6.3 障害時の確認

| 確認対象 | 想定結果 |
|---|---|
| 外部ブラウザ | 新規HTTP接続に失敗 |
| EC2の稼働状態 | Running |
| Apache | active |
| EC2内部のcurl | HTTP 200 OK |
| セキュリティグループ | HTTP 80の許可ルールなし |

これにより、Apache自体の停止とネットワークの通信制御による障害を切り分ける。

## 6.4 復旧方法

セキュリティグループに以下のルールを再追加する。

| タイプ | ポート | 送信元 |
|---|---|---|
| HTTP | TCP 80 | 0.0.0.0/0 |

ルール保存後、ブラウザから再度アクセスする。

## 6.5 復旧判定

以下を満たした場合、復旧成功とする。

- HTTP 80のインバウンドルールが復元されている。
- ブラウザからWebページを表示できる。
- Hello World!が表示される。

**実施ステータス：結果未確認**

実施後に、障害発生時刻・復旧時刻・調査結果・証跡を追記する。

# 8. コスト管理設計

学習環境のため、不要なリソースを常時稼働させない。

基本方針：

1. 使用していないEC2は停止または終了する。
2. EBSなど、EC2停止中も課金され得るリソースを確認する。
3. NAT Gatewayは現段階では作成しない。
4. AWS Billingで利用料金を確認する。
5. 課金アラートの通知先メールアドレスを確認する。
6. 検証終了後は不要なリソースを削除する。

料金アラートは通知機能であり、EC2を自動停止するものではない。

AWSの無料利用条件はアカウントやサービスによって異なるため、構築時点の料金条件を個別に確認する。
